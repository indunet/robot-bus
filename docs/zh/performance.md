# Robot Bus 与 ROS 2 性能对比

[预编码 CDR Topic](#预编码-cdr-topic-对照) · [传感器负载](#相机和激光雷达量级) · [原生 API 的 Topic、Service、Action](#原生-api-性能) · [归档与复现](#归档与复现)

## 2026-11-20 同机复测

Robot Bus 2.4.0 和 ROS 2 Humble 在同一主机上各测三轮。预编码 CDR Topic 使用相同的应用数据、编码和固定发送速率。原生 API 测试分别使用各自的消息与执行器，表中也收录了后来在宿主机进行的部分 Robot Bus 复测。

AMD EPYC 9554 主机（256 逻辑 CPU、755 GiB 内存）运行 Linux 5.15.0-203-generic 和 Docker 29.1.3。容器镜像为 `ros:humble-ros-base`（Ubuntu 22.04.5，x86_64），绑定逻辑 CPU 32–39（8 个物理核心），内存上限为 8 GiB，`/dev/shm` 为 512 MiB。Robot Bus 使用 Rust 1.100.0 和 ZeroMQ 4.3.4。ROS 2 使用 GCC 11.4、`rclcpp` 16.0.21、`rmw_fastrtps_cpp` 6.2.10 和 Fast DDS 2.6.12。两者均为 Release 构建，以 `b9b414e35f0274bdcef19843562ca8ca770d5685` 为基线，并应用归档中的 benchmark 修订。

## 预编码 CDR Topic 对照

此前的 Robot Bus Topic 直接收发裸字节，ROS 2 Topic 使用类型化 `UInt8MultiArray`。这组对照让两边都直接传相同布局的 **80 B CDR**，含 16 B 固定前缀（封装和数组元数据）及 64 B 应用数据。ROS 2 在计时前用实际 RMW 生成并校验模板，测量时使用 `GenericPublisher` 与 `GenericSubscription` 收发序列化缓冲区。两边的发布端复用缓冲区，只写入时间戳、试验轮次和序号，订阅端校验前缀并直接读字段。应用层消息编解码在计时外，DDS 和 ZeroMQ 本身的复制、封帧、排队、转发及回调成本包含在各自结果里。 [ROS 2 序列化发布源码](https://github.com/ros2/rclcpp/blob/16.0.21/rclcpp/src/rclcpp/generic_publisher.cpp#L21-L29) · [ROS 2 序列化订阅源码](https://github.com/ros2/rclcpp/blob/16.0.21/rclcpp/src/rclcpp/generic_subscription.cpp#L42-L48)

两边在同一个 Humble 容器顺序运行，CPU 32–39、8 GiB 内存、512 MiB 共享内存。每条路径各一个发布者和订阅者，一个应用层接收执行器线程。Robot Bus 测 TCP、IPC、inproc，ROS 2 测独立配置的 SHM、回环 UDPv4。固定负载为 1,000、10,000、50,000 条/秒，各跑三轮，发送 3 秒，排空 100 ms。单条延迟各测 500 条。负载下对序号能被 16 整除且已送达的消息采样，包含排空窗口内收到的抽样消息。两边均采用尽力而为语义，ZeroMQ HWM 与 DDS KeepLast 各为 2048。

每格为三轮中位数 [最小值–最大值]。接收速率按发送窗口计算，投递率在排空后计算。尾延迟采用已送达样本的最近秩百分位数。

### 相机和激光雷达量级

上面的对照都是 64 B 应用数据。这组补测换成三种传感器量级的负载，编码方式不变：两边都发送同一份预编码 CDR，应用数据分别是 256 KiB、640×480 RGB（921,600 B）和 1920×1080 RGB（6,220,800 B）。256 KiB 接近一帧中等激光雷达点云或一张压缩图像，后两档是未压缩相机帧。

固定速率为 10 和 30 条/秒，各三轮，发送 3 秒，排空 100 ms。队列深度两边都是 8。64 B 测试用的 2048 深度如果拿来存 1080p，单边队列就超过 12 GiB，也不符合传感器流通常只保留最近几帧的用法。ROS 2 SHM 的单条上限提高到 12 MiB，共享内存段为 128 MiB；64 B 测试的 64 KiB 上限装不下这些帧。UDP 仍是回环，套接字缓冲保持内核默认的 208 KiB。容器限制与前面相同：CPU 32–39、8 GiB 内存、512 MiB `/dev/shm`。

达标条件不变：窗口内收发都达到目标的 90%，排空后丢失不超过 1%。逐条延迟是一次发一条、收到后再发下一条，单条超过 2 秒没有收到就停止该路径，后面的速率试验不再进行。

1080p、30 条/秒大约是 187 MB/s 的应用数据。Robot Bus 的 TCP、IPC、inproc 和 ROS 2 SHM 在这一档都三轮收齐。同一档的逐条 p50 中位数是 SHM 2.7 ms、inproc 5.5 ms、TCP 23.2 ms、IPC 25.2 ms。Robot Bus 的消息要经过 broker，大帧会多一次搬运；SHM 是发布者和订阅者直接共享。

UDP 的 256 KiB 两个速率，以及 640×480 的 30 条/秒，三轮都收齐。更大的帧在第一次跑的时候，逐条采样 2 秒内等不到下一条，速率试验被跳过。这些格子后来用同一套固定速率单独补测，不再做逐条采样。补测结果是：640×480 的 10 条/秒中位丢失 13.33%，1080p 的 10 条/秒中位丢失 10.00%（一轮全部丢失），1080p 的 30 条/秒中位丢失 3.33%，三轮里只有一轮达标。逐条延迟那一列的「—」表示这组没有完整的逐条样本。内核 UDP 套接字缓冲是 208 KiB，一帧比缓冲大，分片会丢。补测日志在 `bench-results/20261120-2132-sensor-payload/udp-rate/`。

日志在 `bench-results/20261120-2132-sensor-payload/`。复现时在同一容器里构建两个 Release 程序，然后运行 [run_sensor.sh](../../benches/topic_cdr_perf/run_sensor.sh)。默认负载和速率就是上面这组，队列深度默认 8。64 B 测试的入口和 Fast DDS 配置没有改。

## 原生 API 性能

Topic 使用 64 B 应用负载和一对发布者与订阅者。Robot Bus 通过 broker 收发裸字节，原生 ZeroMQ HWM 和 WS Subscribe 的服务端队列深度均为 2048。ROS 2 使用类型化 `UInt8MultiArray`、两线程 `MultiThreadedExecutor` 和 best-effort `KeepLast(2048)`，计时包含 ROS 消息编解码。WS Publish 从 WebSocket 发给原生订阅端，WS Subscribe 从原生发布端发给 WebSocket，邦联从 Broker A 发到 Broker B。

每个 Topic 吞吐档发送 1 秒、排空 100 ms，在 100–750,000 Hz 间以 100 Hz 步长搜索。通过一档要求排空后丢失率 ≤ 1%，且发送窗口内收、发速率均达到目标的 90%。表中所选档位均低于搜索上限。单向延迟另做逐条采样，共 500 条。Service 和 Action 各预热 8 次后串行测 32 次，Action 包含一条反馈及最终结果。RPC 的 p99 对单个慢样本敏感。

各格为三轮中位数 [最小值–最大值]。Topic 速率按窗口内同轮唯一接收数计算，投递率按排空后同轮唯一接收数除以发送数计算。RPC 速率按成功完成数除以测量时长计算。Robot Bus 的 WebSocket 各行和 TCP、IPC、inproc 的 Action 来自绑核的宿主机复测，其余行来自同一容器内各自的测量批次。ROS 2 行使用[修正后的独立传输配置](#ros-2-传输复核)。

## ROS 2 传输复核

初始测试把发布者和订阅者放在同一进程，Fast DDS 2.6 默认启用进程内传递，可以绕过传输。在原二进制和容器里，以 20,000 msg/s 两次复跑，原 UDP 配置每轮只发出 21 个 UDP 数据报，关闭进程内传递后则超过 80,000 个。关闭进程内传递后，原 SHM 配置也仍发出约 20,000 个 UDP 数据报，因为 Humble 的 `ROS_LOCALHOST_ONLY=1` 会向 XML 配置额外加入 UDP 和 SHM。原 SHM 和 UDP 两行因此只能作为当时的同进程配置记录。 [Fast DDS 进程内传递](https://fast-dds.docs.eprosima.com/en/2.6.x/fastdds/transport/intraprocess.html) · [Humble RMW 源码](https://github.com/ros2/rmw_fastrtps/blob/6.2.10/rmw_fastrtps_shared_cpp/src/participant.cpp#L145-L162)

修正后的两个 XML 都关闭进程内传递，运行脚本设 `ROS_LOCALHOST_ONLY=0`，UDP XML 仅绑定回环。固定发送约 20,000 条时，两种配置均收齐，单独运行 SHM 时 UDP 发包计数为 0，运行 UDPv4 时为 20,138。配置见 [SHM XML](../../benches/ros2_perf/config/fastdds_shm.xml)和 [UDPv4 XML](../../benches/ros2_perf/config/fastdds_udp.xml)。Fast DDS SHM transport、Data-sharing 和借用消息的零拷贝路径各有独立的配置条件。 [Fast DDS Data-sharing](https://fast-dds.docs.eprosima.com/en/2.6.x/fastdds/transport/datasharing.html)

在旧配置的固定 80,000 msg/s 诊断中，只把执行器由两线程改为一线程，发送窗口内接收量从约 51,000 条升至 80,000 条，说明旧数据也对执行器调度敏感。吞吐搜索结果表示该次搜索所遇到的最高通过档位。各档需独立重复才能判断速率附近的波动。

## Robot Bus 的 WebSocket 与 Action 复测

历史 WS Subscribe 试验记录了 100.1% 的投递率（`sent=151447`、`recv=151595`）。旧计数器会把前一轮仍在队列中的消息计入新一轮。在受控回归中，当轮发送 1 条，共观察到 3 个到达事件，其中同轮唯一消息、跨轮消息和重复消息各 1 条。新计数按轮次和序号区分，正式复测的 77 个 WS 吞吐试验均满足 `recv_send <= recv_final <= sent`。

TCP、IPC 和 inproc 的 Action 用默认 SDK 路径复测。回复入队后唤醒 executor，消除了等待 250 ms 轮询超时的情况。复测在宿主机上绑定 CPU 32–39，沿用预热和采样次数，三轮日志在 `bench-results/20261120-2115-executor-wake/`。该次复测的 WebSocket Action 约为 44 ms，邦联 Action 约为 0.34 ms。

2026-11-21 的 WebSocket 复测在同一宿主机绑核，连续采集改动前（`d24a506`）和改动后各三轮，均在容器的 8 GiB 内存限制之外。WebSocket 服务端和 Rust 客户端都启用了 `TCP_NODELAY`，WS Subscribe 的收件箱也从每 5 ms 轮询改为等待消息。下表对照的是这次宿主机复测的前后数据。

## 归档与复现

初始证据保存在本机 `bench-results/20261120-134156-same-host/`。其中 `run.sh` 是实际运行脚本，`execution.tsv` 记录轮次和退出码，`raw.jsonl` 包含每档计数、窗口时间和延迟样本，`round-*.log` 含完整输出。同目录保留环境、DDS 配置、源码补丁、Cargo 依赖锁定、二进制哈希、`SHA256SUMS` 和一次超时的 Bus 冒烟。传输复核和修正后的 ROS 2 样本分别位于 `bench-results/20261120-183629-ros2-executor-probe/transport/` 与 `isolated/`，各有 XML、环境、UDP 计数和完整日志。

从源码构建的前置步骤见[贡献指南](../../CONTRIBUTING.md)。`just perf` 和 `just perf-ros2` 将本次运行生成的 Markdown 报告写入本机的 `bench-results/`。采样时可以用 `ROBOT_BUS_PERF_SKIP_REPORT=1` 仅保留 Robot Bus 的输出日志，直接运行 `ros2_perf_bench` 时可以用 `ROS2_PERF_REPORT` 指定报告路径。各场景的命令见 [Robot Bus bench](../../benches/robot_bus_perf/README.md)和 [ROS 2 bench](../../benches/ros2_perf/README.md)。流量经过 `Ros2Bridge` 时的双向采样方法与状态见[桥接性能报告](ros2-bridge-perf-report.md)。

每次正式复测记录以下信息。

1. 日期、提交和源码差异、CPU 型号和核心数、内存、OS/内核、容器资源限制、Release 构建工具链、ROS 发行版和 RMW/DDS 版本。
2. 消息类型/大小、收发端数量、进程布局、传输、HWM/QoS、试验时长与排空方式和全部环境覆盖项。
3. 每轮原始计数、统计窗口、延迟样本、失败或跳过记录，以及多轮中位数和波动范围。
